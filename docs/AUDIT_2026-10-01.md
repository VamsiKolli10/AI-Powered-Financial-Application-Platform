# Working-tree audit — 2026-10-01

Reviewed the current uncommitted changes, including the new Kafka retry loop, currency-scoped
reporting, notification handling, gateway status, and dashboard data flow. Two independent
reviewers examined event delivery and the frontend; the primary reviewer examined backend
reporting and verified the highest-priority findings. This is a correctness review of these
changes, not an exhaustive security or infrastructure audit. Application code was not edited
during the initial audit; the authorized fixes are recorded below.

The two independent reviewers reviewed the fixes. Their follow-up identified browser clock skew,

## Findings

### 1. [P1] Kafka retries can prevent recovery after the poll timeout

Location: [libs/events/consumer.py:81](../libs/events/consumer.py#L81)

The inner retry loop does not poll Kafka again until handling and committing the current record
succeed. After the default `max_poll_interval_ms=300000`, aiokafka can leave the consumer group.
While reassignment is pending, its `assignment()` still exposes the previous partitions, so the
loop's ownership check can remain true. The coordinator refuses to rejoin while the fetch idle
time exceeds the poll interval. With another active member, commits can keep failing even after
the handler's dependency recovers, leaving this consumer stuck until restart.

**Evidence:** using the installed `AIOKafkaConsumer`, subscription state, and
`GroupCoordinator.ensure_active_group`, simulated 301 seconds of fetch inactivity and began
reassignment. Three coordinator checks returned `None`, made zero join attempts, and continued
to expose the previous partition. This verifies the implementation path without a live broker.
The fake-consumer test clears its assignment immediately and misses this behavior.

**Fix:** track revocation through a rebalance listener and resume polling when ownership is
revoked, or separate polling from record processing while preserving per-partition ordering and
safe commits. Add a regression that models aiokafka's retained assignment, then validate recovery
against a live broker with a shortened poll interval and another group member.

**Origin:** introduced by the latest retry fix. Resolve this before relying on its recovery claims.

### 2. [P1] Budget-alert deduplication crosses user and currency boundaries

Location: [services/notifications/rules.py:100](../services/notifications/rules.py#L100)

The key `budget:{category}:{YYYY-MM}` omits the user and currency. NotificationRepository looks up
that key globally, and the database makes it globally unique. The first user's groceries alert
therefore suppresses another user's groceries alert for the same month. A USD alert also
suppresses an EUR alert for that category and month.

**Evidence:** a synthetic SQLite reproduction attempted user A/USD, user B/USD, and user A/EUR
alerts. Only the first was stored; both later alerts were suppressed. All three generated the
same key.

**Fix:** include user identity and currency in budget keys. Test different users and currencies,
as well as replay of the exact same alert. Consider existing stored keys when choosing migration
or compatibility behavior.

**Origin:** user collision predates the latest changes; the currency filtering changes leave the
currency collision unresolved.

### 3. [P2] Future transactions inflate dashboard period totals

Location: [web/src/api.ts:62](../web/src/api.ts#L62)

`getPeriodTransactions` sends a start bound but no `to` bound. Ingestion permits future
`occurred_at` timestamps, and transaction listing includes them. Insights ends its reporting
window at the current server time, so a credit dated tomorrow inflates Money in and Cash flow
while Money out still covers the period to date.

**Evidence:** a temporary frontend test returned a future credit and confirmed the request
omitted `to` and accepted the credit into the period's items.

**Fix:** capture an end time once and use it across all pages; align the transaction and summary
reporting windows. Add coverage with both future credits and future outflows.

**Origin:** current dashboard implementation.

### 4. [P2] Period changes relabel old figures before new data arrives

Location: [web/src/features/Dashboard.tsx:178](../web/src/features/Dashboard.tsx#L178)

Selecting Week immediately passes the new period into MetricsRow but retains the monthly summary
and transactions until the new requests settle. Monthly totals and comparison percentages are
temporarily presented as weekly figures. Only the spending panel gets the refreshing state.

**Evidence:** a temporary component test held the weekly summary request pending. Monthly
spending of $1,700 and a +20% comparison appeared with `vs last week`; the monthly credit also
appeared with `this week`.

**Fix:** store the loaded period alongside its figures, or clear/show loading for the metrics
during refresh. Test the intermediate state, not just the final response.

**Origin:** current dashboard implementation.

### 5. [P2] Empty spending state hides excluded-currency spending

Location: [web/src/features/SpendingPanel.tsx:25](../web/src/features/SpendingPanel.tsx#L25)

When the report currency is USD but spending exists only in EUR, Insights correctly returns no
USD category rows and `other_currencies: ["EUR"]`. The panel instead says there is no spending
and omits the exclusion note because that note is nested inside the nonempty branch.

**Evidence:** a temporary component test rendered that response and observed “No spending
recorded this month yet” with no EUR explanation.

**Fix:** qualify the empty state by report currency and render the exclusion notice independently
of category rows.

**Origin:** current currency-aware dashboard implementation.

### 6. [P2] Assistant answers silently exclude other currencies

Locations: [services/assistant/retrieval.py:222](../services/assistant/retrieval.py#L222),
[services/assistant/answers.py:64](../services/assistant/answers.py#L64)

Retrieval selects the primary account currency but does not preserve which currencies were
excluded. Draft answers and facts therefore cannot explain an incomplete spending total. In a
USD account with EUR-only transactions, the assistant says it sees no transactions at all.

**Evidence:** a synthetic SQLite ledger with a USD account and a €500 outflow produced:
“I don't see any transactions for October 2026.”

**Fix:** carry excluded-currency information into retrieved context, facts, and drafts. Qualify
empty and partial answers by currency; provide a supported way to request the other currencies.

**Origin:** current currency filtering changes.

### 7. [P2] Largest-transaction retrieval filters after limiting the candidate set

Location: [services/assistant/retrieval.py:263](../services/assistant/retrieval.py#L263)

The assistant takes only the 100 most recent transactions, then filters by currency and sorts
by amount. It can miss the true largest outflow. A hundred newer foreign-currency transactions
can also remove every candidate even though the primary currency has spending in the window.

**Evidence:** a synthetic ledger containing an older $1,000 purchase and 100 newer €1 purchases
returned USD total spend of $1,000 but an empty largest-transactions list.

**Fix:** query the owned accounts, reporting window, currency, and outflow condition in SQL,
order by amount with a deterministic tie-breaker, and then limit to the required results.

**Origin:** the original 100-record cutoff predates these changes; post-limit currency filtering
adds another failure case.

### 8. [P2] Stored alerts suppress delivery retries

Location: [services/notifications/handlers.py:91](../services/notifications/handlers.py#L91)

Notifications are committed before channel delivery. If `channel.send` raises, the next handler
attempt suppresses the stored notification as a duplicate and performs no delivery. The handler
then succeeds, permitting Kafka acknowledgement even though delivery never succeeded.

**Evidence:** the independent reviewer reproduced two handler calls with a failing delivery
channel: one delivery attempt, zero delivered alerts, and one stored alert.

**Fix:** persist delivery state or use a delivery outbox so retrying storage does not erase the
remaining delivery work. Test failure after commit and recovery on a later attempt.

**Origin:** preexisting. Production currently uses LoggingChannel, so present exposure is limited;
this matters before adding an external delivery adapter. The stored in-app notification remains
available despite a channel failure.
